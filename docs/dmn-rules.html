DMN Decision Tables — User Guide

Decision tables bring predictable, table-driven automation to your Jira issues. Instead of chaining dozens of if/then rules, you describe outcomes in a grid and let the app pick the right action for each situation. This guide explains how decision tables work in this app and how to build one that does exactly what you need.

Overview

A decision table is a compact grid that maps combinations of issue attributes (the inputs) to the actions the app should take (the outputs). It is inspired by the DMN standard, but has been tailored to work natively with Jira issues and the app's automation engine.

Each automation rule can contain:

  • One trigger — the event that starts the rule (e.g. Issue Created).
  • One or more conditions — combined with logical AND.
  • One decision table — the grid described in this guide.
  • One or more standard actions — executed regardless of the table.

When a trigger fires, the engine checks the conditions and, if they pass, evaluates the decision table. Any outputs the matched rows produce are then executed against the Jira issue.

Where do I find this?

Decision tables live inside each automation rule, in the 📊 Decision Table (DMN) section of the rule card. Open BPMN, Workflow Automation & Portfolio Manager from the Jira app launcher, open a diagram's automation rules, and expand a rule to see the table.

Anatomy of a Decision Table

A decision table has three parts:

  1. Input columns — issue fields that the engine inspects (e.g. Priority, Issue Type).
  2. Output columns — the actions to take when a row matches.
  3. Rows — each row is one rule. A row "matches" when all of its non-empty input cells match the current issue.

Here is a complete example:

Hit policy: First (F) — the first matching row wins.
# PriorityInput Issue TypeInput ActionOutput
1 High Bug transition: In Progress
2 High (any) assign: 5f4b...
3 (any) (any) add_comment: Triaged by automation
Empty cells are wildcards

If an input cell is left blank, the engine treats that cell as matching any value. This lets you write catch-all rows without listing every combination.

Hit Policies

The hit policy tells the engine how to behave when more than one row matches. Choose it from the dropdown directly above the table.

Policy Code Behaviour when multiple rows match
Unique U Exactly one row must match. If two or more rows match, no outputs are produced (the table is considered ambiguous).
First default F The first matching row (in table order, top to bottom) wins. Evaluation stops after the first match.
Collect C All matching rows contribute their outputs. Every match is executed.
Any A All matching rows must agree on every output value. If they disagree, no outputs are produced.
When to choose which
  • First — for prioritised escalation rules ("the most specific rule that applies").
  • Collect — when you want to apply several independent actions, e.g. add a label and post a comment.
  • Unique — to enforce that your table is unambiguous; great as a safety check.
  • Any — for consensus rules where conflicting matches should silently do nothing.

Input Columns

An input column inspects a single Jira field. The column's label determines which field is read — the label is matched (case-insensitive, spaces removed) against the supported field names below.

Label (use any case) Jira field read How the value is compared
statusIssue status nameEquals, compared case-insensitively
priorityPriority nameEquals, case-insensitive
issuetypeIssue type nameEquals, case-insensitive
assigneeAssignee display nameEquals, case-insensitive
labelsComma-joined label listEquals the whole string, case-insensitive
componentsComma-joined component namesEquals the whole string, case-insensitive
Comparison is "equals"

Inside a decision table, every non-empty input cell is compared using equals (case-insensitive). The richer condition operators (contains, greater than, etc.) are available in the separate If (Conditions) block of the rule, not inside the table cells themselves.

Use the + Add Input button to add a column. You can rename a column by editing the header text directly, and remove it with the ✕ button next to the label. Removing a column also strips its cells from every row.

Output Columns

An output column holds the action the app will perform when a row matches. To be treated as an actionable output, the column's label must contain the word "action" (case-insensitive) — for example Action, Routing Action, or Escalation Action. Output columns whose labels do not contain "action" are ignored by the engine.

The value of an output cell uses a keyword prefix to select the action type:

Output cell value Action performed Example
transition: <status> Transitions the issue to the named status (matched case-insensitively against the workflow's transition names). transition: In Progress
assign: <accountId> Assigns the issue to the given Atlassian account ID. assign: 5f4b9a2c8e1f0100
Any other value Added as a comment on the issue. Auto-triaged as P1.
Output cells are free text — be exact

The prefix (transition: / assign:) must be spelt exactly, in lowercase, followed by the value. Anything else is posted verbatim as a comment. If a transition or assignee value doesn't resolve in Jira, that single action is skipped — the rest of the rule still runs.

Actions & Output Syntax

Decision table outputs support three keyword actions (transition:, assign:, and free-text comments). For richer actions — setting fields, adding or removing labels, creating linked issues, or calling webhooks — use the rule's separate ✅ Then (Actions) block. Those standard actions run in addition to the decision table outputs whenever the rule fires.

Standard action type Value format What it does
Set Field Value<field>:<value>Sets a single issue field.
Transition Issue<status name>Transitions to the named status.
Add Comment<text>Adds a comment.
Assign To<accountId>Assigns the issue.
Add Label<label>Adds a label.
Remove Label<label>Removes a label.
Create Linked Issue<proj>|<type>|<summary>Creates a new issue.
Call Webhook<URL>POSTs the issue JSON to the URL.

Conditions

The rule-level If (Conditions) block is evaluated before the decision table. All conditions must be true (logical AND) for the table to be evaluated at all. Conditions support the following operators:

OperatorMeaning
equalsExact, case-insensitive match.
not_equalsAnything other than an exact match.
containsThe field value includes the given substring.
not_containsThe field value does not include the substring.
is_emptyThe field has no value.
is_not_emptyThe field has any value.
greater_thanNumeric greater-than.
less_thanNumeric less-than.
Conditions vs. decision table inputs

Conditions are good for broad gates ("only when status = Open"). Decision table inputs are good for branching outcomes across many combinations. You can use both together: a few conditions to gate the rule, then a decision table to pick the precise action.

Triggers

A rule begins with a single trigger — the event in Jira that causes the engine to evaluate it. The trigger also restricts which decision-table evaluations make sense.

TriggerFires when…
Issue CreatedA new issue is created.
Issue UpdatedAn issue is updated (any field).
Issue TransitionedThe issue's status changes. You can restrict this to a target status using the "To status" field.
Priority ChangedThe priority field changes.
Issue AssignedThe assignee field changes.
Comment AddedA comment is added.
Self-generated events are ignored

To prevent infinite loops, the engine skips any event caused by the app itself. You don't need to add your own loop guard — but keep it in mind if a rule seems to "do nothing": the triggering change may have been made by this app.

Evaluation Order

For each project diagram, when a trigger event arrives the engine does the following:

  1. Re-fetches the full issue from Jira (the webhook payload is minimal).
  2. Derives the specific trigger type from the event and changelog.
  3. For each active rule on the diagram whose trigger matches the event type:
  4. Validates any trigger-specific config (e.g. the target status for transitions).
  5. Evaluates the rule's conditions (logical AND). Skips the rule if any fail.
  6. Evaluates the decision table per the chosen hit policy.
  7. Executes the rule's standard actions, then the decision-table outputs, against the issue.
Each action is independent

If one action fails (for example, an invalid transition name), it is logged and skipped; the remaining actions still run. This means a single bad cell value won't silently kill your whole rule.

Worked Examples

1. Priority-based triage (First hit policy)

When a bug is created, escalate it immediately; otherwise add a generic comment.

Trigger: Issue Created · Hit policy: First (F)
# PriorityInput Issue TypeInput ActionOutput
1HighBugtransition: In Progress
2Auto-triaged. A teammate will review shortly.

2. Multi-label routing (Collect hit policy)

Apply several labels based on issue type, regardless of priority.

Trigger: Issue Created · Hit policy: Collect (C)
# Issue TypeInput ActionOutput
1Bugadd_label: needs-triage
2Taskadd_label: backlog
3Epicadd_label: planning
Mixing decision outputs and standard actions

add_label: is not a decision-table keyword, so in row cells it would be posted as a comment. To actually add labels here, either move add_label into the rule's ✅ Then (Actions) block (one per label) or keep the table for routing and add labels as standard actions.

3. Assignment routing (Unique hit policy)

Assign issues to a dedicated owner per component. If two components match, do nothing.

Trigger: Issue Created · Hit policy: Unique (U)
# ComponentsInput ActionOutput
1Frontendassign: 5f4b9a2c8e1f0100
2Backendassign: 6a7c1b3d902f0200
3Infraassign: 7b8d2c4e013f0300

How to Build a Decision Table

  1. Open the diagram whose rules you want to automate and expand the Automation Rules panel.
  2. Click + New Rule and give it a name.
  3. Under ⚡ When (Trigger), choose the event that should start the rule.
  4. (Optional) Add gate conditions under 🔍 If (Conditions).
  5. In the 📊 Decision Table (DMN) section, pick a hit policy.
  6. Use + Add Input and + Add Output to define columns. Rename headers so inputs match a supported field name and outputs contain the word "action".
  7. Use + Add Row to add rules. Fill in input cells (leave blank for "any") and output cells using the output syntax.
  8. (Optional) Add standard actions under ✅ Then (Actions).
  9. Click Save Rules. Your changes persist to the app storage and begin firing immediately.
Drafts are auto-saved

While editing, your unsaved changes are kept as a local draft so switching tabs or reloading won't lose work. A banner reminds you to press Save Rules to persist them to the server.

Best Practices

  • Order rows from most specific to least specific when using the First hit policy, since the first match wins.
  • Keep a catch-all row at the bottom (all input cells blank) so unexpected combinations still get a sensible default action.
  • Name output columns with "action" — columns without that word in the label are ignored by the engine.
  • Prefer Collect when you want multiple independent actions; Unique when ambiguity should be a no-op.
  • Test with a real issue after saving — create or update an issue that should match and watch the resulting comment/transition.
  • Disable rules while editing if you don't want them firing mid-edit; re-enable after saving.

FAQ

My table didn't fire. Why?

Common causes:

  • The rule is disabled (toggle the Enable button).
  • The trigger type doesn't match the event that occurred.
  • A rule-level condition failed, so the table was never evaluated.
  • For Issue Transitioned, the target To status didn't match the issue's new status.
  • A Unique or Any policy produced no output because rows conflicted.

Why did my output become a comment instead of an action?

The output cell value must start with exactly transition: or assign: (lowercase, with the colon). Anything else — including a typo like Transition: or transition with no colon — is posted verbatim as a comment.

Can a decision table use "contains" or "greater than"?

Not inside the table cells — table inputs always use case-insensitive equals. For those operators, add a rule-level condition in the If (Conditions) block.

Does the app look at custom fields?

Custom fields are supported in the Conditions block (choose Custom Field and enter the field id). They are not directly addressable as decision table input columns.
